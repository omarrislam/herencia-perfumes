## Post-M4 round 27 (ntfy owner purchase alerts + two production bugs found & fixed, DEPLOYED api, 2026-07-12)
- ✅ **Push notification to the owner's phone on every new order** via ntfy.sh (free, no account) — `apps/api/src/lib/ntfy.ts` mirrors the `waCloud.ts` pattern: env-gated (`NTFY_TOPIC` presence = enabled), fail-soft (try/catch, never breaks checkout), called once from `createOrder` after the WhatsApp receipt send. Fires for new orders only (COD confirmed or InstaPay pending), not later status changes. Title `New order HRC-XXXX — EGP 450`, body = customer name+phone/line items/payment, priority high, tag 💰, tap opens `<CLIENT_ORIGIN>/admin/orders`.
- 🐛 **Bug #1 (found live, first deploy sent zero notifications):** the original implementation used ntfy's **header-based publish API** (`Title`/`Priority`/`Tags` HTTP headers). Fetch/undici require header values to be **ByteString (Latin-1 only)** — the title's em dash (—, U+2014) is outside that range, so every real send threw `Cannot convert argument to a ByteString…`, caught by our own try/catch and silently logged server-side. **Unit tests didn't catch it** because they fully mock `global.fetch`, which bypasses real Headers validation entirely — a live reproduction (placing a real order against `localhost` hitting the shared prod DB) was needed to surface the actual error. **Fix:** switched to ntfy's **JSON publish API** (`POST {server}/` with a JSON body containing `topic/title/message/priority/tags/click`) — no header involved, so no ByteString hazard for any future unicode (accented/Arabic customer names included). Gotcha: the JSON API requires `priority` as a **number** (1–5); the string form (`"high"`) that the header API accepts is rejected with a generic `400 invalid request: request body must be valid JSON`.
- 🐛 **Bug #2 (found live, second deploy still sent zero notifications):** `NTFY_TOPIC` was set on Vercel via `echo "value" | vercel env add …` — `echo` appends a trailing `\n`, and `vercel env add` stores the entire stdin verbatim, so the stored value was `"herencia-orders-x2026\n"`. With the old header/URL-path approach this was silently trimmed by URL parsing; once the topic moved into the **JSON body**, ntfy received the literal trailing newline and rejected it outright (`400 topic invalid`). **Fix:** `vercel env rm` + re-add via `printf '%s' "value" | vercel env add …` (no trailing newline). **Lesson for any future Vercel secret via this CLI: never pipe `echo` into `vercel env add` — use `printf '%s'`.**
